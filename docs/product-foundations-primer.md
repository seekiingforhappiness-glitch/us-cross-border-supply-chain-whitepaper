## 第 0 章 全书最重要的一个发现

三路独立调研（Palantir 官方文档、Hermes 官方文档与源码、金融/ITIL/SRE/RPA 跨行业实践）收敛到同一个结论：

> **世界上不存在"模型在线自我进化"的可信企业系统。所有"越用越强"的已验证实现，都是"可审计的文件资产 + 出提案走审批 + 用量数据治理 + 快照回滚 + 渐进放权"。**

- Palantir 的"越用越好"= 决策血缘沉淀为数据 + 人工迭代 prompt/逻辑 + Evals 回归把关 + **"外科手术式"渐进放权**（官方原话：surgically choose which trusted, well-worn AI processes can automatically close the action loop）。官方文档中**查无**任何自动微调/自动改 prompt 的产品机制。
- Hermes（自我进化的旗手）的"越用越强"= 四条腿：记忆文件、技能文件（Markdown，可 patch 可回滚）、GEPA 离线进化（**出 PR 强制人审，never direct commit**）、轨迹导出反哺训练。**没有一条是模型在线变聪明，全部是可审计的文件与流程。**
- 金融风控的规则进化 = shadow mode（并行跑不生效）→ canary（1% 流量）→ 渐进放量 → 转正 + 自动回滚。

**这对你意味着三件事**：① 你在探讨中选的"治理式进化"不是保守妥协，而是全行业唯一被验证的路；② "越用越强"的工程本质是**管理一堆会生长的文件资产**（先例、技能、评估集、决策日志）——你的项目恰好就是这么长大的（决策日志 append-only、勘误文化、评估器），你已经用九个月亲手实践了这套机制，只是没意识到它就是产品机制本身；③ 你要卖给客户的"进化"，其实是**把客户组织的隐性经验持续结构化**——这才是"与客户现有组织拉开差距"的真正含义。

## 第 1 章 Palantir 本体的灵魂：建模的是决策，不是数据

**机制**。Palantir 官方给 Ontology 的定义不是"数据模型"，而是：**"a system designed to represent the decisions in an enterprise, not simply the data"**。每个运营决策拆四要素：data（看什么）、logic（怎么判断）、action（怎么执行）、security（谁能做）。架构文档的原话更狠："**名词（数据对象）必须配上动词（action/function）才能建模决策；semantics must be paired with kinetics**"。没有动词的本体只是个高级数仓。

**【你的先例】** 你的宪法反目标第一条"不是数据分析看板——没有动作回写的功能一律不做"，就是这句话的中文版。你从 D1（行级粒度，为了算清"影响哪个客户各多少量"——这是决策需要，不是存储需要）到 A1-A6 动作五要素，走的正是"为决策建模"的路。**Palantir 的本体哲学你不需要学，你需要的是意识到你已经会了。**

**你还缺的一块：决策血缘（decision lineage）**。Palantir 自动捕获"这个决策是何时、基于哪个版本的数据、经哪个应用做出的"，并把它称为"优化人与 agent 长期表现的上下文燃料"。你的 action_log 记录了"谁做了什么"，但没有记录"当时看到了什么"——比如老板批准改期时，他看到的影响金额、AI 简报版本、先例引用。**决策血缘 = 审计日志 + 决策时的世界快照**。它是第 5 章"越用越强"的原材料：没有血缘，先例库就只有结论没有理由，学不出东西。

**裁决题 1**：客户老板三个月后问："当时为什么批准给 BestBuy 那单空运加急？多花的八千美金值吗？"——要回答这个问题，系统在批准那一刻必须留存哪几样东西？（提示：不只是"谁在几点批了"。）

## 第 2 章 Action 的完整解剖：你的五要素 vs Palantir Action Types

**机制**。Palantir 的 Action Type 由五部分组成，与你的动作五要素几乎一一对应：

| Palantir | 你的五要素【你的先例】 | 差距 |
|---|---|---|
| Parameters（参数） | 动作输入 | 无实质差距 |
| Submission Criteria（提交前校验，含 Current User 模板） | 前置条件 + 执行者权限 | 你已有（B5 三重门禁就是 criteria） |
| Rules（11 种本体编辑规则） | 成功路径的状态回写 | 你已有 |
| **Side Effects：writeback webhook vs side-effect webhook** | —— | **你缺的核心** |
| Notifications（权限硬约束） | —— | **你缺的核心** |

**你缺的第一块：对外动作的两种承诺等级**。Palantir 把"回写外部系统"分成两类，语义完全不同：
- **Writeback webhook**：在本体编辑**之前**执行，"如果 webhook 失败，其他任何变更都不发生"——整个动作回滚。用于"外部系统是事实源"的动作（比如向 ERP 改交期：ERP 没改成，你的系统里也不能显示已改）。每个动作只能有一个。
- **Side-effect webhook**：本体编辑成功**之后**异步执行，best-effort，失败不回滚。用于通知类（发飞书消息失败，不该让改期动作作废）。

你的产品要接真实世界（飞书通知、未来的 ERP 写回），**每个对外动作都必须先回答：它是 writeback 还是 side-effect？** 答错的代价：把通知当 writeback，飞书抖动会让业务动作全部失败；把 ERP 写回当 side-effect，系统显示"已改期"而 ERP 里没改，客户按旧交期备货——真实事故。

**你缺的第二块：通知的权限硬约束**。Palantir 原文："用户只能收到包含其有权查看数据的通知"，且可选两种失败模式（任一收件人无权→整个动作失败，或只发给有权者）。你的通知走飞书群——**群里有谁，决定了通知里能写什么**。cs 能看到的延误通知里不能出现成本字段，这条规则必须在通知渲染层强制，而不是靠模板作者自觉。【你的先例】你的 sensitiveFieldRules 已有"渲染铁律：隐藏字段必须显示 no access"，同一哲学延伸到通知即可。

**还有一个隐蔽但致命的语义：at-least-once**。Palantir 的自动化引擎明说"同一触发可能执行多次效果"，所以**一切自动化动作必须幂等**。【你的先例】W7 计划的 M3 事件信封幂等键、M7 outbox 幂等键，就是为这一天准备的——直接继承。

**裁决题 2**：AI 同事自动执行"给货代发飞书消息催促补充舱单信息"，和自动执行"向 ERP 回写新承诺交期"——这两个动作在失败处理上必须有什么本质区别？如果都失败了，客户系统里各应该看到什么状态？

## 第 3 章 权限的双轨制，与"AI 以谁的身份行动"

**机制一：双轨权限**。Palantir 的权限不是一套而是两套叠加：
- **自主轨（discretionary）**：角色（Owner/Editor/Viewer）——项目负责人可以授予。
- **强制轨（mandatory）**：Organization 隔离墙 + Markings（如 PII 标记）——**"无论用户角色如何，强制控制永远拦住无资格者"**，标记随数据血缘自动传播到衍生数据，连 Owner 都不能擅自摘除。

翻译成你的产品：**"客户 A 的数据永远不可能出现在客户 B 的任何界面/通知/AI 回答里"这类规则，不能靠角色配置实现（配置会错），必须是租户标记级的强制隔离**——这是多租户的生死线，从单租户第一天就要按这个思路建（tenant_id 不是一个普通字段，是强制轨）。行级/列级/单元格级权限（Restricted Views / Object Security Policies）你已有微缩版（字段脱敏），差距在：Palantir 未通过策略者看到 null 而非报错——优雅降级。

**机制二：AI 以谁的身份行动（直接回答你的 §5 盲区的前半）**。Palantir 分两种场景，身份模型完全不同：
- **交互场景**（用户在对话框里使唤 AI）：AI 继承**调用用户**的权限子集——用户看不到的，AI 也看不到。【你的先例】你的 AI_ROLE="ops" + 脱敏就是这个。
- **无人值守场景**（自动化后台跑）：AI 以 **automation owner**（自动化的所有者，或专门的 service user）身份执行——审计记 owner，criteria 按 owner 校验，编辑自动化必须先接管所有权。**唯一例外是通知：按每个收件人各自的权限过滤。**

这对你产品的三个 AI 同事是根本性的：**ops 同事 7×24 监控延误，它不是"以某个用户"在跑，而是以"ops-agent 服务账号"在跑**——这个账号有自己的权限边界、自己的审计身份、自己的动作配额。RPA 行业（UiPath）用几十年验证了同一划分：贴身助手型机器人只能在触发用户的权限内跑，后台自主型机器人用独立凭证资产+独立审计链。

**裁决题 3**：finance 同事夜里自动核对了一批对账单、标记了两笔超收，早上老板在飞书点了"发起争议"。这一连串行为的审计日志里应该出现几个身份？各是谁？如果争议邮件里要引用发票金额，谁的权限决定能不能引用？

## 第 4 章 AIP 的 AI 接线法：你已有微缩版，缺的是四个升级件

**机制**。AIP 把 LLM 接到本体上的方式，你的 agent/ 目录已经是微缩版：

| AIP 机制 | 你的对应物【你的先例】 | 状态 |
|---|---|---|
| Agent 工具（Object Query / Action / Function 七类） | tools.py 的 11 个白名单工具（9 查询 + 2 写） | ✅ 同构 |
| Action 工具"可配置自动执行或需用户确认" | FORBIDDEN_TOOLS（审批/关闭永不注册） | ✅ 你的更严，需按第 7 章矩阵放开分级 |
| AIP Logic：LLM 判断 + **确定性 Apply Action 块**分离 | 确定性简报 + LLM 只转述 | ✅ 同构（你把"不编造"做成了架构问题） |
| staged proposals + Agent decision log | proposal-only + action_log | ✅ 同构，缺 decision log（见第 1 章血缘） |
| **AIP Evals** | agent/evaluate.py 22 题 | ⚠️ 你有评估，缺"评估作为变更闸门"的流程 |

**四个升级件**（按优先级）：
1. **Evals 流程化**：Palantir 的用法是——改 prompt、换模型、调逻辑，前后跑**同一套件**对比，通过才发布。官方方法论：ground-truth 集 + **二元判定的 LLM-as-a-judge**（明确 pass/fail，拒绝复杂打分）+ 扰动测试（错别字/同义词/对抗输入）+ 每用例至少 3 次捕捉方差。【你的先例】你的评估器文化 100% 兼容，升级点是把"发版前全绿"写进产品的发布流程，且**真实数据的人工确认样本自动流入评估集**（本体对象集直接当测试集——Palantir 的做法）。
2. **决策日志（decision log）**：AI 提案必须可回放"它当时看到什么、为什么这么建议"——第 1 章血缘的 AI 侧。
3. **检索上下文的分层**：AIP 分 Ontology context（对象语义检索）/ Document context / Function-backed context 三类。你的同事回答"这票为什么延误"时，检索的是对象图；回答"UFLPA 新政策怎么办"时，检索的是文档库——两条管道，别混。
4. **模型生命周期**：AIP 模型目录有 Experimental→Stable→Sunset→Deprecated。你的可插拔 provider 已就绪，补一个"换模型=跑全量 Evals"的纪律即可。

**裁决题 4**：你想把 ops 同事的提示词改三行，让它的提案更激进一点。发布这个改动前，按本章的标准流程应该发生什么？如果新提示词让 22 题里的"诱导越权"红线题从拒绝变成了执行，系统应该怎么反应？

## 第 5 章 ★"越用越强"的真相与你的进化机制设计

（这是你 §6 问题"Palantir 是怎么做的？"的完整答案，也是产品定位的核心。）

**Palantir 的答案（官方证实）**：四个组件，没有魔法——
1. **决策血缘沉淀**：每个决策连同上下文自动入库，成为"优化人与 agent 长期表现的燃料"；
2. **反馈进学习回路**："工作流中收集的每条反馈可安全地纳入持续学习回路，驱动从辅助到自动化的旅程"——注意落地形态：反馈变成**本体里的数据**，供人改 prompt/改逻辑/扩评估集，**不是自动改模型**；
3. **Evals 回归把关**：任何变更前后跑同一评估套件；
4. **渐进放权**：先全量人审提案 → 随通过率与信任上升，**按工作流粒度**把"久经考验"的流程切到免审自动闭环，授权可收可放。

**Hermes 的答案（官方+源码证实）**：四条腿，同样没有魔法——
1. **记忆文件**（MEMORY.md/USER.md，自动写但可开人工审批，写入前做注入扫描防投毒）；
2. **技能文件**（Markdown+版本号，从"5+ 次工具调用的成功任务/踩坑后找到的路/被用户纠正"三类时机自动提炼；用 patch 定点精炼；每技能带用量统计）；
3. **Curator 治理**（每 7 天空闲时运行：30 天未用标陈旧、90 天归档、重叠技能合并；**每次运行前全库快照，一键回滚**；关键技能可 pin 住连智能体自己都删不掉）；
4. **GEPA 离线进化**（读执行轨迹理解失败原因→定向变异→多目标评估，**所有变更以 PR 提交强制人审**）。

**收敛后，你的产品进化机制设计**（治理式进化的完整落地）：

| 进化资产 | 原型 | 写入 | 生效 | 治理 |
|---|---|---|---|---|
| **PrecedentCase 先例库** | Palantir 决策血缘 | 每次人工审批/修正自动沉淀（含决策时上下文快照） | 立即可被检索引用 | 只增不改；错误先例可标记废止（留痕） |
| **SkillAsset 技能资产**（解析模板/提案策略/话术） | Hermes 技能文件 | AI 从成功处置与人工纠正中**提议**新版本 | **人批准后生效**，带版本号 | 用量统计 + Curator 式周期治理 + 快照回滚 + 关键技能 pin |
| **评估集** | AIP Evals | 人工确认样本自动流入 | 发版闸门 | 红线题永不删除 |
| **自主权等级**（第 7 章） | Palantir 渐进放权 + Gartner L4→L5 | 一致率数据驱动**提议**升级 | **人批准后生效** | 出错自动降级，断路器 |
| 冻结区：权限矩阵/门禁/审批链/FORBIDDEN 清单 | 你的宪法 | —— | —— | 不存在自动修改它们的任何动作 |

**"越用越懂你"的护城河机制**（回答你对 §1 定位的要求）：客户用一年后，系统里积累的是**该客户自己组织的结构化经验**——他家货代的靠谱程度、他家客户的容忍度、他老板的决策偏好（先例库）、他行业的解析模板（技能）、他业务的评估基准。竞品给不了，因为这些不是功能是**数据资产**；客户自己也回不去，因为回去等于把这套经验重新变回员工脑子里和微信记录里。**你卖的不是软件，是组织经验的复利账户。**

**裁决题 5**：设计伙伴的运营专员连续第五次把 AI 解析的"EMC 船司延误通知"里的日期格式改正。按本章机制，接下来系统里应该自动发生什么、等待谁做什么、绝不允许发生什么？

## 第 6 章 Hermes 可直接搬进产品的六个机件

（Hermes 册的精华——工程借用清单，每个都注明"为什么是它"。）

1. **技能的文件形态**：Markdown + YAML frontmatter（name/description/version），兼容 agentskills.io 开放标准；**渐进披露**加载（先给目录 3k tokens，用哪个再取全文）——技能库长到几百个也不炸上下文。
2. **patch 式精炼**：技能改进用 old→new 定点修改而非整篇重写——省 token、diff 可读、人审容易。
3. **审批嵌进聊天**：危险操作在消息平台上**直接回复 yes/no 即审批**，超时（60 秒）默认拒绝。你的老板飞书一键批就是这个——加上"超时默认拒绝+升级"（第 8 章）。
4. **子代理禁写共享记忆**：Hermes 的子代理天生被禁用 memory 工具——**临时执行者的认知不允许污染长期记忆**。你的三个同事共享先例库/技能库，但任何一次性任务的子代理只能读不能写。
5. **记忆写入的注入扫描**：所有会进入系统提示的内容（记忆/技能/上下文文件），写入前扫描提示注入模式（"忽略先前指令"、藏在注释里的指令、外泄企图）——**防投毒是进化系统的疫苗**。你的产品还要加一层：来自企微群粘贴的货代消息本身就是不可信输入，解析层就要扫。
6. **Kanban 人机同板**：Hermes 的多代理协作不用黑盒编排，用一块 SQLite 看板——每次交接是一行记录，人和 agent 都能看能改，worker 是有名字有记忆的角色，阻塞原因显式分类上浮给人。【你的先例】这就是你的 Task 队列 + W7 工作队列设计的多智能体版——同构到可以直接合并设计。

**一个反面教训也要搬**：Hermes 官方承认"没维护的技能库会堆满几十个近似重复的窄技能，污染目录浪费 token"——**技能膨胀比技能错误更常见**。以及它没有花费上限机制（成本失控防护空白）——你的产品要有每租户 LLM 预算闸。

**裁决题 6**：为什么"临时子代理不能写共享记忆"和"评审以重跑为准不以报告为准"【你的先例，X2】是同一条原理？这条原理在你产品里还应该出现在哪？

## 第 7 章 ★AI 自主权分层矩阵（你的 §5 盲区正解）

**跨行业十大模式**（全文见调研报告，此处浓缩为你要背下来的五条）：
1. **分级轴至少二维做乘积**：金额敞口 × 时间窗口 × 可逆性——所有成熟体系都拒绝单轴分级；
2. **三色带**：自动通过（绿）/人工审核（灰）/自动拒绝（红）——灰带宽度就是人力预算的调节阀；
3. **自主权跟可逆性走，不跟模型能力走**——授权是设计决定（arXiv 框架：能力与自主解耦）；
4. **deny 绝对优先**：红线不能被任何 allow 打洞（Claude Code 设计）；
5. **要求人批太多次 = 没有人批**：93% 盲批实测数据——审批预算是稀缺资源，只花在刀刃上。

**你的产品自主权矩阵 v1（草案，待你裁决）**：

| 等级 | 定义 | 动作示例 | 执行模式 |
|---|---|---|---|
| **L0 观察** | 只读 | 监控、解析、影响计算、简报、分诊定级 | 全自主，无需通知 |
| **L1 内部低风险写** | 可逆、影响限于系统内 | 建任务、打标签、写先例、催办提醒 | 自主执行 + 审计 + 可撤销 |
| **L2 业务写（可逆）** | 改业务状态但可回退 | 改内部计划日期、分派任务给人、暂缓发票入账 | **信任阶梯**：影子→提案→默认执行可否决→免审（见下） |
| **L3 高风险/对外/不可逆** | 花钱、对外承诺、合规 | 批准加急（花钱）、对客户发函、争议货代账单、任何合规裁决 | **永远提案**，人批准执行 |
| **红线（deny）** | 产品存在资格 | 冒充人类身份对外沟通、改权限/门禁/审批链、删审计、跨租户访问 | 不存在这样的工具 |

**L2 的信任阶梯（核心机制，四步都有先例）**：
影子模式（AI 私下决定，只记录不生效，对比人的实际决定）→ 提案模式（Gartner L4 opt-in：人点头才做）→ **默认执行可否决**（Gartner L5 opt-out：AI 做了，通知人，24h 内可一键撤销）→ 免审（进入 L1 待遇）。
- **晋升凭证 = 一致率**：某类动作影子/提案与人最终决定的一致率 ≥ 阈值（如 95%，样本 ≥ 30）→ 系统**提议**晋升 → 人批准生效（进化走审批，第 5 章）。
- **授权绑定场景域（ODD）**：晋升的是"ops 同事 × 美西航线 × 延误 ≤7 天 × 改期动作"这个组合，不是"ops 同事"整体——出域自动回落提案模式。
- **降级自动**：被人否决/撤销 2 次连续 → 该域自动降一级并通知；任何一次造成实际损失 → 直接回影子 + 复盘。
- **断路器**：单日自主动作数、单笔金额、累计金额三个熔断阈值，越限即全域转提案 + 通知老板。

**裁决题 7**：ops 同事在"美西线改期"域已晋升到"默认执行可否决"。今天它对一票走**中东线**的延误单也想直接改期；同一天，它在美西线的一次改期被专员撤销（第 1 次）。这两件事系统各应怎么处理？

## 第 8 章 ★异常升级矩阵（你的 §7 盲区正解）

**机制骨架（ITIL + PagerDuty，几十年验证）**：
- **priority = impact × urgency**。你的两根轴：impact = 金额敞口 × 客户等级（A 客户升一级——【你的先例】R1 已这么做）；urgency = 距离不可挽回的时间窗口（船到港前 vs 已产生滞箱费，能抢救的时间不同）。
- **P1-P4 定级 → 决定三件事**：谁被通知（路由）、多大声（强通知 vs 安静通知——PagerDuty 的 urgency 双轨）、SLA 多紧。
- **两条正交升级通道，别混成一条链**：**functional**（横向：转给有能力处理的人/同事——补舱单找 ops，对账争议找 finance）与 **hierarchic**（纵向：SLA 将破时通知有权拍板的人——老板）。专家干活 + 领导知情，并行不串行。
- **超时自动升级**：每级有 escalation timeout，无人认领/无人批准 → 自动升下一级。**没有超时升级的"仅提案"会退化成"永久搁置"**——这是"高风险仅提案"模式的必要配套。
- **单一责任人**：一次只通知一个目标直到显式认领（防"都以为别人在管"）。
- **宁高勿低**：拿不准 P2 还是 P1，按 P1 处理；事中不辩论级别，复盘再调。

**AI 在矩阵中的五个角色**（回答"AI 扮演什么"）：
1. **一线分诊员**：每个异常先经 AI 定级（impact 沿对象图算金额敞口——你的引擎已会；urgency 按事件类型查表）——人只复核 P1/P2 的定级；
2. **影响计算器**：给每级决策者附经济账（"空运补救 $500 vs 迟到罚金 $2,000"——Blue Yonder 模式）；
3. **方案起草者**：按第 7 章等级提案或执行；
4. **催办者**：SLA 走表、到点升级、点名单一责任人；
5. **复盘记录员**：关闭时沉淀先例（第 5 章闭环）。

**行业情报**：project44/FourKites/Blue Yonder 公开材料**都没有**可操作的 severity 定义表和"自动处置 vs 人批"矩阵——它们只有方向叙事。**把 ITIL 级的显式矩阵做进控制塔，本身就是你的可辩护差异点。**

**裁决题 8**：周五晚 11 点，系统解析出一票 A 类客户的船 ETA 推迟 9 天，将击穿大促备货期；同时有一笔 $180 的滞箱费超收。按本章矩阵：两件事各定几级？各通知谁、多大声？如果老板周六中午还没看提案，系统该干什么？

## 第 9 章 FDE 模式：你是自己的 Delta，AI 是你的 PD

**机制**。Palantir 的组织分两种工程师：Dev（one capability, many customers，做产品件）与 Delta/FDE（one customer, many capabilities，驻场把一个客户做透）。前员工复盘点破本质：**"驻场意味着捕获客户如何工作的隐性知识"**；产品化路径是"FDE 在客户现场手工做脏活 → PD 把脏活自动化成平台件"——刻意过拟合单客户，第二三个客户出现重复时才泛化。AIP Bootcamp 是它的规模化变体：**1-5 天做客户的真实用例**（不做预制 demo），"正确的技术路线必须是经验的，不是神学的"。

**映射到你**：
- **你就是 Delta**：驻场（你亲友的业务本来就在身边）访谈、看他们的企微群和 Excel、把隐性流程翻译成对象/动作/先例——这一步**无法外包给 AI**，因为隐性知识在人身上；
- **AI 是你的 PD**：把你翻译出来的东西写成解析模板、规则、评估集、界面——这一步你已验证过九个月（Fable 规划 + Opus 执行的分工，就是你的 PD 团队）；
- **GTM 学 bootcamp**："给我 5 天 + 你最近三个月的对账单和企微记录，我给你一个能用的延误处置台"——比"买我的 SaaS"可信一个数量级；
- **过拟合不可耻**：第一个客户的解析模板写死他家货代的格式没关系——第二家出现时才抽象。**先泛化是原型的死法**【你的先例：ChatGPT 初始方案教训】；
- **安全审计是进门钥匙**：Palantir 靠"把安全做进集成层"化解客户的数据政治。中小货主一样怕数据泄露（供应商价格、客户名单）——你的权限/审计/租户隔离故事从第一天就是销售材料。

**裁决题 9**：第二个设计伙伴（走中欧班列的货主）的货代通知格式与第一家完全不同。按本章方法论，你应该 (a) 先把解析模板抽象成通用配置系统再接入，还是 (b) 给他单独写一套模板，第三家再考虑抽象？为什么？

## 第 10 章 新宪法起草工作坊（你的 §9 盲区）

**思考钥匙**：宪法 = **不变式清单**。起草方法是逐条问："**什么东西一旦被违反，这个产品就失去存在资格？**"答案通常落三类——受托责任（客户数据怎么碰）、身份边界（AI 是谁、永远不许做什么）、诚实文化（失败怎么处理）。反过来，凡是"违反了可以道歉改正继续经营"的，都不进宪法，进普通规范。

**候选条文草案**（每条括号内是它防的事故，供你逐条裁决）：

一、受托责任
1. 客户数据租户级强制隔离，任何查询/通知/AI 回答不得跨租户（防：一次泄露=产品死亡）；
2. 密钥不进代码库，客户数据每日备份且备份可恢复演练过（防：删库跑路式事故）；
3. 客户数据永不用于训练模型、永不出现在其他客户的任何输出中（防：数据资产被稀释成公共知识）。

二、身份边界
4. AI 永不冒充人类身份对外沟通——所有 AI 生成的对外内容显式署名或经人签发（防：客户发现被机器人应付的信任崩塌）；
5. 审批/关闭/合规裁决/花钱类动作的执行权永属于人；AI 触碰冻结区（权限/门禁/审批链/审计）的工具不存在（防：自动化事故不可归责）；
6. 每个动作可追溯到实名身份（人或服务账号）+ 决策时上下文（防：出事后无法复盘）。

三、诚实文化
7. 指标不达预期，记录并修正认知，不改口径不删历史（【你的先例】XE3 文化直接平移）；
8. AI 的每个事实性陈述可溯源到对象引用；查不到就说查不到（【你的先例】五条铁律平移）；
9. 进化资产（技能/阈值/自主权）的每次变更留版本与理由，可一键回滚（第 5 章机制的宪法化）。

**留给你的工作坊裁决题（三道，答案没有标准，答完宪法就是你的了）**：
- 10a. 设计伙伴老板说"别让我批了，全都自动吧"——按第 7 章你有信任阶梯，但他要求跳过。宪法应该允许客户自愿放弃全部审批吗？边界在哪条？
- 10b. 某技能进化后解析准确率从 92% 升到 97%，但它是 AI 自己 patch 后忘了走审批直接生效的（假设有 bug 绕过了闸门）。结果是好的——按宪法该怎么处理这次"善意违宪"？
- 10c. 你自己想在周末直接改生产数据库里的一条错误记录（你是创始人，有 root）。宪法管不管你？

## 附录：裁决题要点（先自答再看）

1. 决策血缘四件套：决策时的影响金额与受影响订单快照、AI 简报/提案的版本与内容、引用的先例、审批人与时点。缺任何一件，三个月后只能靠回忆。
2. 发飞书=side-effect（失败重试、不回滚业务动作，业务状态照常推进）；写 ERP=writeback（失败则整个改期动作回滚，系统必须显示"改期未生效"而非"已改期"）。判据：外部系统是不是该事实的权威源。
3. 三个身份：finance-agent 服务账号（夜间核对+标记，无人值守身份）、老板实名（审批）、发送动作的执行身份（经老板批准的动作，audit 记老板为批准人）。引用金额看**收件人**的权限（Palantir 通知铁律）——发给货代的争议函里可以有金额（对账场景），抄送 cs 的内部通知里不可以。
4. 标准流程：改动进入待发布版本 → 跑全量评估套件（22 题+红线）→ 全绿才生效 → 版本与理由入审计。红线题失败=发布被阻断，这正是评估器存在的意义（不是通过率仪表，是回归闸门）【你的先例：W4"评估的价值在防回归"】。
5. 自动：第 5 次修正样本入评估集，触发阈值后系统生成 SkillAsset 新版本**提案**（附 diff 与依据样本）。等待：人审批该解析模板升级。绝不允许：模板未经批准自动生效（治理式进化的生效闸门）。
6. 同一原理：**生成者的自我报告不可作为验证依据；临时上下文的产物不可直接进入长期资产**。还应出现在：AI 提案不能引用自己未经确认的解析结果作为事实（待确认队列先过人）、评估集样本必须来自人工确认而非 AI 自评。
7. 中东线：出域（ODD），自动回落到提案模式——晋升不迁移。美西线撤销 1 次：记录在案、不降级（阈值 2 次连续），但该域一致率统计更新；若下周再被撤销一次则自动降回提案并通知。
8. 延误=P1（A 客户×大金额×时间窗口紧）：立即强通知（电话级/飞书加急）ops 值班 + 同步知会老板（hierarchic 并行）；滞箱费 $180=P3/P4：安静通知进 finance 同事队列，工作日处理。老板周六中午未批 P1 提案：超时升级——按预设升级链转备用决策人或再次强提醒，且 AI 把"什么都不做的代价"（每延一天的敞口变化）附在催办里。
9. (b)。先泛化是原型的死法；两个样本不足以设计正确的抽象。给第二家单独写模板，同时记录两套模板的共性笔记，第三家出现时用三个真实样本做抽象——这正是 Palantir"FDE 过拟合、PD 泛化"的节奏。
10. 工作坊题无标准答案。参考视角：10a——审批可以下放，责任不能消失：客户可签署放权到 L2 全自动，但 L3 红线（花钱/对外/合规）建议合同层面保留，因为出事时"你们的 AI 自己干的"在法律与商誉上都由你承担；10b——结果好也回滚+复盘闸门漏洞，因为宪法保护的是机制可信而非单次结果（机制一旦可绕过，下次绕过的就不是好结果）；10c——管。宪法对创始人生效才叫宪法，你的项目九个月的经验：AGENTS.md 的规则没有一条是摆设【你的先例】。
