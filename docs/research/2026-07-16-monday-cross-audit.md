# 以 monday 为镜的全维度审计与升级方案（综合稿）

## 【总判断】

我们与 monday 的架构 **DNA 同源**——两边都走"先定边界 → 有类型的数据模型 → 命令层收口所有写入 → 视图与数据分离 → 规则引擎 → 外部系统隔离 → AI 小步可测 → 可控 Agent → 评测护栏渐进上线"这条主线，逐阶段能对上。整体水平上，我们在**验收门严格度、治理深度（权限/审计/脱敏/规则可复现）、AI 安全对抗**这几处**达到或超过** monday；真正的短板集中在"该做成可配置数据的东西还写死在代码里"和"渐进放权只走了四档中的一档"。

成熟度路径形态不同：monday 是**一条产品爬阶梯的直线**，我们是**螺旋**（MVP → 成熟度补强 → 六业务域横铺 → 产品形态重构），所以我们的门不是"每阶段一道"，而是"**每次建模变更一次人批**"。

**最值得向 monday 学的 Top 3**：① 渐进上线里的"**影子模式**"（让 AI 在旁边跑历史案例、只记录不生效，用证据挣信任——我们的零件已散落 80% 却从没组装起来）；② **"把配置写成可保存的数据、而不是写死在代码里"** 这套声明式思路（我们在权限/工具/关系这些治理层已经做到，但规则逻辑和视图层还是硬编码）；③ **每次改动都带的"通用工程契约"**（先写测试、小改动、五句复述——monday 写在每个任务末尾，我们只活在部分模板里，走别的流程就整条漏掉）。

**我们已经不输甚至更强的**：UI 和 AI 都不能直接写库（全走命令层）、对象-关系图谱（胜过 monday 的固定三级容器）、288 条注入对抗全拒、出境隐私摘除 + 审计不留原文、决策日志逐字人批。

**一条诚实提醒**：monday 本身是**空脚手架 + 方法论文档**，它没有一套比我们成熟的实现。本次审计比的是**打法对照**，不是"它有个更强的代码"——凡是判"缺口"的地方，是我们对照它的方法论确有没做到的，不是它做出来了而我们没有。

## 【一】真架构缺口 · 值得补 · 纯工程可执行

> 分三梯队。第一梯队是"我们声称做到、但实际有洞"的必修项（诚实红线，小改动堵漏）；第二梯队是把治理从"文档承诺"变成"看得见的证据"的战略工程；第三梯队是低成本收口。

### 第一梯队：必修的真洞（小改动，堵住我们声称做到却有缺口的地方）

**1.1 `close_risk_event` 关闭动作不是原子的（准 bug，最该先修）**
- **monday 怎么做**：任何命令失败不留半成品（要么全成、要么全不成）。
- **我们缺什么**：其他动作（指派/提案/审批）都用了事务包装器 `transaction()`，唯独 `close_risk_event` 裸跑多条写（`app/actions.py`：取消任务 L646、回滚行状态 L649、更新风险 L661、`backfill_outcome` L665、`_log` L667），末尾单发 `con.commit()`（L670），**无回滚保护**。若中途抛异常，前面的改动已执行未提交，且异常会**穿透抛给调用方**——同时违反本文件顶部"从不抛异常给调用方"的契约和 monday"失败不留半成品"。
- **升级建议**：把这段写操作套进 `with transaction(con)` + `try/except → _fail`，和 `approve_mitigation` 对齐。
- **工作量：小**。

**1.2 两人同时改同一条记录会"后者覆盖前者"（乐观锁 / 并发窗口）**
- **白话**：乐观锁 = 改一条记录前先看它有没有被别人动过，动过就拒绝、而不是闷头覆盖。我们现在没有这个保护。
- **monday 怎么做**：所有更新带 version（版本号），写时校验版本没变过才写。
- **我们缺什么**：35 个对象**无一有 version 列**；状态机的读检查（"这条还是 open 吗"）**发生在事务之外**（`app/actions.py:303` 先 SELECT、312 检查、321 才进事务），中间存在"两个审批人都读到同一状态、都通过检查、都写入"的时间窗（维度②③一致确认）。
- **强诚实标注**：SQLite 写串行化 + 状态机守卫把后果**收窄**了——**单用户 demo 里几乎不触发（低危）**；只有在产品化设想的"多专员并发工作台"里才是中危。
- **升级建议**：**最小修法**（纯工程可立即做）——把状态机 SELECT **移进事务内**，让"检查+写"在写锁下原子化，先堵窗口。**完整修法**（加 version 列 + 写时校验）是否上，取决于"多用户并发是否进当前范围"→ 这个优先级归第二节裁决。
- **工作量：最小修法 小；完整 version 列 中**。

**1.3 部分风险规则重跑会产生重复事件（幂等不对称）**
- **白话**：幂等 = 同一个扫描重复跑，结果和跑一次一样，不会重复堆数据。
- **monday 怎么做**：规则可重放、重跑不重复产生。
- **我们缺什么**：R1-R6 按自然键**合并**（重跑近似幂等），但 R7-R21 是 `seq = count(*)` 然后**恒 INSERT**（`engine/` 的 `apply_procurement/warehouse/sourcing/finance_candidates`），在非空表上重跑会**产生重复风险事件**。现在不出事只是因为"每次建全新空表 + 检测只跑一次"，**不是重跑安全**（维度⑤指认为唯一真算 bug 的幂等缺口）。
- **升级建议**：把 R7-R21 的"count+恒 INSERT"改成按自然键 upsert（对齐 R1-R6 的合并语义）。
- **工作量：小**。

### 第二梯队：战略工程（把治理变成看得见的证据——最高价值）

**1.4 影子测量台（本次审计里战略价值最高的一件，且零件已散落 80%）**
- **白话**：让 AI 在旁边把历史风险案例都跑一遍、给出它会提的处置建议，**只记录不生效**，然后和"确定性引擎/种子里的标准处置"对比一致率。这台机器是"以后要不要给 AI 更多权限"的唯一证据来源。
- **monday 怎么做**：渐进上线四档里的 shadow（影子）档——风险最低、专门用来挣信任。
- **我们缺什么**：仓库里"影子模式"这个词有，但指的是 DDL schema 比对（和 AI 无关）和一段未来机制的文字描述，**没有任何代码**把 AI 提案和人的真实决定做一致率对比。而组件都在了——`agent/evaluate.py --llm` 能让真 AI 过题、`resolution_memory` 已归档"决定+结果"、`llm_calls` 已采遥测——**从没被组装成一台测量机**。
- **升级建议**：把这三个零件组装成"AI 提案 vs 确定性/种子决定的批量一致率测量"，**合成数据上就能完整跑，不改任何线上行为**。
- **工作量：中**。

**1.5 一页运行看板（直击项目北极星"系统看不见 = 病根"）**
- **monday 怎么做**：一页聚合看板——金标通过率、注入结果、越权计数、预算达标一屏可见。
- **我们缺什么**：`llm_calls` 遥测**只写不展示**（全仓只有测试和自检读它），288 注入结果、golden 通过率、越权计数都散在 CLI 的 stdout 里，**没有任何 UI 视图聚合**。数据全在，只差一个控制室视图。
- **升级建议**：建一个控制室页面，聚合 `llm_calls` + `action_log` + eval 结果。
- **工作量：中**。

**1.6 规则执行台账（每次风险扫描留一笔可复盘、可重放的账）**
- **白话**：每次跑风险扫描都记一笔——用的哪版规则、扫的哪天数据、输入数据的指纹、扫出多少、有没有出错。以后能 diff、能重放、能回归。
- **monday 怎么做**：规则执行记录规则版本 + 输入 + 结果 + 错误，旧运行仍可复现。
- **我们缺什么**：`engine/` 全线不带规则版本戳（grep `rule_version` 零命中），`action_log` 记了规则 id/结果，但没记版本和可重放的输入指纹。
- **升级建议**：新建一张**旁路运行台账表**（不碰核心对象），每次 detect 落一条 `rule_id + rule_version + as_of + 输入指纹 + 产出数 + result/error`。
- **⚠️ 审计师分歧点（原样交回，不替你选边）**：维度⑤把"规则版本可追溯"判为**纯工程**（走这张旁路台账）；维度①把它判为**需你裁决**（因为维度①设想的实现是给核心对象 RiskEvent **加一列** `detected_by_rule_version`，会触发真值 md5 基线重算，须走变更协议）。**二者其实是两条实现路径不是硬矛盾**——旁路台账绕开了真值基线、纯工程可先做；"给 RiskEvent 行内加版本戳"才需要你拍（见第二节）。建议先做旁路台账。
- **工作量：中**。

### 第三梯队：低成本收口

**1.7 sim 活世界层没被主发版门覆盖**
- **我们缺什么**：`sim/`（3699 行，明确定为"重投入板块"）自带完整验收 `sim/verify.py`，但发版清单 `docs/release-checklist.md §0` 的一键复现链**不含** `sim.backfill`/`sim.verify`，ONBOARDING 五分钟路径 grep `sim.` 零命中——**最重投入的新层回归风险裸奔**。
- **升级建议**：把 `python3 -m sim.backfill && python3 -m sim.verify` 加进 release-checklist §0 和 A 门，ONBOARDING 补一行。

**1.8 提案的值级校验偏弱（只查字段在不在，不查类型/范围）**
- **我们缺什么**：`PARAM_SCHEMAS`（`app/actions.py:44-58`）是"必填键子集检查"，不校验类型/枚举/数值范围——比如 expedite 只查 `est_cost_usd` 这个键在不在，不查它是不是正数（维度③⑥一致）。
- **升级建议**：把 `PARAM_SCHEMAS` 从"字段集合"升级为"字段→(类型,约束)"，一处补齐所有提案类型。

**1.11 决策日志模板加"删除/回退方案"栏**

- **工作量：中**。

## 【二】真架构缺口 · 值得补 · 需 Daniel 业务裁决

> 这些涉及建模/范围/放权分级/产品方向，工程不能自作主张。建议集中开一次"方向裁决会"拍板。

### 裁决题 1：AI 放权分级——要不要引入 auto（自动执行）档？
- **为什么值得**：monday 渐进上线是四档（影子→建议→审批→自动），我们只恒定在"建议+审批"一档。
- **为什么需要你裁决**：放权是**不可逆的信任决定**。⚠️ 澄清一个命名陷阱——本体里 `ai_executable:"auto"` 的 7 个动作**不是**自动执行，运行时不变式证明它等价于"AI 可作为提案人调用"，真正的决定动作全是 `frozen`。所以**我们现在没有 monday 的 auto**。项目自己白纸黑字把放权冻结在"接真实数据 + 受控试点 + 影子一致率达标"之后（六阶段门）。
- **给你的选项**：**A** 继续冻结在 proposal-only/maker-checker（符合现有风险纪律）；**B** 等影子测量台（1.4）达标后按域逐步放权。**无论选哪个，影子台都该先建**（已在第一节，不占这次裁决）。置信度门（低置信转人工）随 auto 一起立项——现在单独补是"空补"（没有自动路径可拦）。
- **附带文档动作**：给 `ai_executable:"auto"` 改名或加注释（如 `ai_proposable`），消除"auto=自动执行"的误读，否则迟早骗到未来接手的人。

### 裁决题 2：谁编写风险规则？（决定要不要把规则逻辑数据驱动化）
- **为什么值得**：monday 把规则做成可编辑的 JSON，我们把规则逻辑写死在 Python（治理层反而是数据驱动的——轴押的位置不同）。
- **为什么需要你裁决**：这是**产品定位问题不是工程问题**，且不可逆（投规则 DSL 是数月级投入）。crux 就一句话：**供应链经理需要自己编写风险规则吗？**
- **给你的选项**：**A**「规则库是我们策展的领域 IP、用户只调阈值」→ 保持逻辑在代码，只把本体 `riskRules` 的散文描述升级为半结构化契约就够（低成本）；**B**「用户要自编规则」→ 才值得投一个比 monday 更富、能表达时序窗口和图遍历的规则 DSL（大动作）。
- **提醒**：改阈值已经是纯配置（改 YAML 不改代码），所以"用户调参数"这条已解决；这道题只关"用户改规则结构"。

### 裁决题 3：产品形态——单租户 FDE 交付，还是多客户 SaaS？（一道元裁决，下挂四项）
- **为什么值得**：这道题一拍，下面四个"以后再补很贵"的横切改造才有方向：
  - **多租户隔离**（tenant_id）：现在 35 个对象无一带租户维度，`action_log`、6998 条关系边都假设单库单租户——文档已选定"一租户一库文件"方案，但**隔离改造是横切全栈的、不是加一列能了事**。
  - **person 一等身份对象**：现在 `assignee_user_id` 只是引用一个 demo 花名册，没有真正的负责人/团队/通知（依赖飞书身份集成）。
  - **受治理字段的自助加字段向导**：不能放开"用户随手加自由列"（会击穿"本体是治理唯一权威源"这条宪法），但若要客户方 CSM 自助加字段，需要建一个"强制填类型/敏感性/归属"的字段向导。
  - **终端用户自定义/保存视图**（和第一节的 ViewConfig 分歧联动）。
- **为什么需要你裁决**：这些全绑定"是否走多客户"这个**商业定位**，且越晚补越贵。注意 `apps/freight-audit-agent/` 已是第二垂直，portfolio 化苗头出现。
- **给你的选项**：**A** 保持单租户 FDE 中介式改本体（现状已足够、更安全，四项都不立项）；**B** 转多客户 SaaS（则四项按此优先级依次立项）。**当前阶段不建议提前建**——但你要知道翻转成本。

### 裁决题 4：对外闭环的雄心——API 重试语义 + outbox 覆盖哪些外部副作用？
- **为什么值得**：本分支正是 API 层（三座桥 + MCP）。一旦动作暴露为网络 API，会被重试；且现在 outbox（对外部系统的"待办意图"账本）**只接了 1 个动作**（reschedule），expedite/suspend_supplier 等约 14 个处置在现实里同样是对外部系统的副作用，却只写本地表。
- **为什么需要你裁决**：这关系到 **demo 想展示多少"闭环写回外部系统"的能力**——决定叙事雄心，不是工程能定的。
- **给你的选项**：**API 重试**——是否承诺 at-least-once 语义、要不要在 Command 层加 idempotency_key 回放（重试返回原结果 vs 返回状态冲突错误，二者体验不同）；**outbox 覆盖**——哪些处置动作建模成"写回外部系统"、target_system 怎么切分。裁定后落地是纯工程。

### 裁决题 5：接真实客户数据（A 能力）的时机与介质
- **为什么值得**：治理地基（出境隐私闸、血缘、MDM）已建且强于典型系统，缺的是"第一个真实客户的那几种介质"的窄适配。
- **为什么需要你裁决**：**A 启动的第一动作是你主导的介质普查**——真实数据以什么介质/格式/频率到达（EDI / Excel / API / 邮件附件？）。顺序不能反，否则是"没看数据就自信空建"。接哪个系统（飞书/企微/EDI）取决于普查结果。入口签名/限流是接真实推送的硬前置，现在零骨架，**A 节点触发、不该现在抢跑**。
- **给你的选项**：先定"何时启动 A"→ 做半天介质普查 → 再据此建窄 ingest 适配。

### 裁决题 6：防篡改审计要不要入跨境合规叙事？
- **为什么值得**：`action_log` 现在是普通可变表（自述"no immutable audit backend"），无哈希链/防篡改。跨境合规场景里"审计不可篡改"往往是卖点。
- **为什么需要你裁决**：这取决于**对外叙事**——demo 只讲"可解释可回放"当前足够；若审计完整性是卖点，才升级为哈希链/append-only 后端。
- **给你的选项**：**A** demo 阶段维持现状；**B** 若入合规叙事则立项防篡改后端。

### 裁决题 7：工程微纪律要不要写进 AGENTS.md 宪法？
- **为什么值得**：monday 的"先写测试/小改动/五句复述/窄测试"是每个任务末尾的通用约束，人人必带；我们这些纪律真实存在，但只活在部分模板里——**走别的流程的会话会整条漏掉**（grep AGENTS.md 对"失败测试/复述/小 diff"全部零命中）。
- **为什么需要你裁决**：内容是纯工程，但**改 AGENTS.md 宪法须你批准**（§9 规定）。
- **给你的选项**：**A** 维持现状（靠执行者选对流程）；**B** 把 8 条通用约束写进宪法强制，从"模板惯例"升级为"宪法强制"。

6. **出境隐私摘除闸 + 审计不落原文**——主动摘手机/邮箱/身份证/银行卡 + 业务编号白名单，比 monday 被动日志脱敏更彻底（维度⑦⑥）。

## 【四】领域差异 · 不适用 · 不必补（避免盲目照抄）

1. **多租户 tenant_id**——单租户 FDE demo 当前不适用（产品化会翻转，见裁决题 3）。
2. **用户运行时加自由列**——会击穿"本体是治理唯一权威源"宪法，已用"schema-as-code 重生成"解决且更可治理（新字段自动获得校验/脱敏/影子对比）。
3. **入站 webhook 签名/限流 + 真实外部系统 + outbox 异步分发器/超时重试 worker**——反目标不接真实 API，无 inbound 通道可超时，M7 已把它写成人批过的显式缓建，A 能力接真实数据前不适用。
4. **monday 的 equals/and 条件 DSL**——表达不了我们的时序/图计算（事件流重算、N:M 分配 JOIN、跨对象传导），直接照搬是"用上一个范式的胜负手量新范式"。
5. **事件驱动触发器（item.created）+ Jobs/scheduler 原语**——仿真世界的 as_of 批处理是合理的刻意简化，接真实事件流前无落点。
6. **AI 步骤的 input_hash（参数哈希）**——我们刻意存全参可取证（单租户 demo + 已过出境隐私摘除闸），比哈希更有用。
7. **富工作台逐对象 / 七区 SQL 口径逐区硬编码**——领域语义不可约，per-object/per-zone 是正确的，强行配置化会牺牲"可回查一手口径"这条红线；Kanban 对 RouteMap/AI 工作流等领域可视化也无意义。
