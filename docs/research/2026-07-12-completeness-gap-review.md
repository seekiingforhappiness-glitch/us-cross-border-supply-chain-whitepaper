## 第一档：不补会在阶段 1（4 周设计伙伴验证期内）就出事

**G1. 产品自身的"哑火"监控与降级行为**【完全缺席；LLM 预算闸提了一句但触发后行为没设计】
全文的"监控"都是 AI 监控货（7×24 监控延误），没有一处讨论"谁监控系统本身"。解析管道静默死亡、LLM API 不可用、每租户预算闸触发后解析是否停摆、飞书发送失败时 P1 如何送达——都无设计。核心验收断言"每周 ≥1 次系统先于人发现异常"依赖管道活着，而管道死了没人知道，这是对自身承诺的直接威胁。

**G2. 工作台的用户认证与公网部署安全**【完全缺席】
授权（authorization）设计很厚（双轨权限、字段脱敏、tenant_id 钢印），但认证（authentication）零讨论：专员 Web 工作台怎么登录、会话管理、与飞书身份如何绑定、单台国内云服务器上 Streamlit 级应用的公网暴露面。真实客户数据 + 无认证设计 = 宪法第①条"一次泄露=产品死亡"最可能的实际触发点。

**G3. 对外触达通道与发件身份**【完全缺席】
自主权矩阵把"催货代补舱单、对客户发函、争议货代账单"列为核心动作示例，宪法④也规定了 AI 署名——但署了名的信**从哪个口发出去**全文没有答案：用邮件还是企微？用谁的账号（企微对外部联系人没有机器人通道）？送达如何确认（§8 说"动作有回执才算完成"）？交互层只设计了内部（飞书机器人+工作台），接入层只进不出。阶段 1 第一次执行 L3 提案就会撞上。

**G4. LLM 供应商的数据出境与处理条款**【完全缺席】
默认 OpenAI + 部署在国内云服务器：客户企微原始消息（含货代联系人姓名电话等个人信息）送往境外 API 的 PIPL 数据出境问题、OpenAI API 对中国大陆的官方可用性（历来受限，需核实现状——这同时是合规问题和第一天的连通性问题）、与 LLM 供应商的数据处理协议，均未讨论。宪法只约束了"客户数据永不训练模型、不跨租户"，没约束"原始数据送给哪家外部处理者、在哪个法域处理"。"安全审计是销售材料"的叙事（§2）在客户追问这一条时会当场破功。

## 第二档：阶段 2（付费/多租户/第二家客户）前必须补

**G5. 客户离开路径：数据导出、交还、销毁、退款**【完全缺席】
且与卖点直接矛盾：§1 说先例库/技能资产"是客户自己的数据资产"，但全文唯一一次"导出"出现在租户隔离条款里；客户终止合作时数据以什么格式交还、何时销毁、退款条款——三条异常路径（退款/导出全部数据/删除数据）全部无答案。"是你的资产但拿不走"撑不过第一份正式合同谈判。

**G6. 数据保留与删除义务的张力**【完全缺席】
RawMessage 不可变、先例只增不改、审计不可删——三条"永不删"设计与个人信息删除权/客户删数要求正面冲突，谁赢没有裁决；数据只增长，归档策略也无。

**G7. 商业化要素：定价/试用/发票/续费/计量**【完全缺席；合同"提了一句但没设计"——宪法⑤证明想过合同存在，但合同本体（责任上限、SLA 条款、DPA）零设计】
连"设计伙伴期收不收费"都未写。

**G8. AI 出错的对客责任与补偿**【提了一句但没设计】
内部机制完整（撤销归因、降级、复盘），但错误造成客户真金白银损失后：道歉与补偿机制、"AI 提案+老板批准=责任怎么分"的对客说法，没有讨论。最终落点是 G7 的合同责任条款，两条连体。

**G9. SkillAsset 的知识产权归属与跨客户抽象边界**【完全缺席】
三次法则明确计划"第三家出现才抽象成通用配置"——即把从客户 A/B 数据里长出的解析模板变成产品资产；而销售叙事说这些是"客户自己的数据资产、竞品带不走"。抽象后的通用技能归谁、算不算变相"客户数据出现在他租户"，在第二家客户签约前必须有答案，否则两个卖点互相拆台。

**G10. 时间维度：节假日/旺季/时区/夜间静默**【完全缺席】
无业务日历概念：春节/国庆货代与专员集体停摆时，超时升级链会按 SLA 疯狂空转升级；旺季（黑五备货季）异常峰值撞上"老板日批 ≤5 件"的审批预算，无降级策略；跨时区日期解析影响 urgency 计算；P1 强通知（电话级）的夜间/值班规则未定义。**若阶段 1 的 4 周验证期撞上国庆，此项提前变成第一档。**

**G11. 运营者手册与单人连续性**【完全缺席】
谁培训客户专员、培训材料与用户文档、客户提 bug 走什么通道、对客户的产品级 SLA 承诺（全文的 SLA 都是系统内部异常处置 SLA，不是"产品对客户"的可用性承诺）、Daniel 生病/度假时 7×24 承诺谁兜底（bus factor = 1）、数据泄露真发生后的响应与告知预案——宪法说"一次泄露=产品死亡"，但没有"真泄露了第一小时干什么"。

**G12. 产品关停/创始人退出时的客户保障**【完全缺席】
产品定位就是"锁定客户组织经验"，一人公司的存续风险是客户老板最自然的尽调问题：数据托管/源码托管（escrow）承诺、最短关停通知期，无任何讨论。设计自己写了失败出口（"第 12 周人工负担未降=产品失败"），但没写宣布失败后设计伙伴的数据与业务怎么退场。

## 第三档：记录即可

**G13. 跨客户网络效应**【完全缺席——"根本没想"而非"想过后放弃"】宪法③封死了朴素版，但匿名聚合基准（航线延误基准、货代靠谱度、费用行情比价）要不要做、如何与宪法相容，未权衡。
**G14. 续费与流失挽回旅程**【完全缺席】旅程后半段整体空白（阶段 1 可原谅）。
**G15. 租户内人员流动**【完全缺席】专员离职/老板换人后，AutonomyGrant 的一致率成绩单（对着旧决策人训练出来的）与先例中的"老板偏好"是否仍有效，未讨论。
**G16. 状态页/发布节奏/维护窗口沟通**【完全缺席】Evals 闸门管"能不能发"，没管"何时发、怎么告知客户"。

## 已覆盖、不报（核对过的框架项）

备份与恢复演练；AI 可解释性给客户的形态（决策血缘四件套、经济账简报、对象 ID 引用）；客户对 AI 决策的申诉（否决/撤销+归因分类）；发现与上线旅程（bootcamp GTM+设计伙伴）；老板/专员双角色日常旅程；内部异常 SLA 与升级链；提示注入防护（教材第 6 章已定——**但提醒：v2 规格正文并未收录这条，写实施计划时别落下**）。

## 一句话总评

设计在"系统运行中"这一段近乎全覆盖，缺口集中在三个盲区——**系统自己坏掉时**（G1-G4）、**钱和法律进场时**（G5-G9）、**时间和人不配合时**（G10-G12）。最危险的两条：G1（自身承诺无自监控兜底）和 G5+G9 组合（"客户的数据资产"叙事与导出缺席、跨客户抽象计划三者互相矛盾，会在销售场景被同一个问题击穿）。
