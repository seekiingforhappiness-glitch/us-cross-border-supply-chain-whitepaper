## 一、五维度诊断（我们真有的 vs 真缺的）

### ① 底层逻辑

**真有**：真事务（BEGIN IMMEDIATE + 写锁复检 + SAVEPOINT 嵌套）；规则检测自然键幂等（21 规则，
两次重跑实证不翻倍）；action_log 全量审计 + trace_id 血缘（AI 写透传、人工 NULL，本日 A-1
浏览器亲验再证）；maker-checker 双人复核；四本账分立（action_log/llm_calls/rule_run_ledger/
dq_issues）≈ Monday 四类日志分离的雏形。

**真缺**（全为【通用】级，不是 SaaS 税）：
- **单一 Command 写信封**：写入口已收敛到 app.actions 同一批函数（好），但没有统一信封——
  无 command_id、无动作级幂等键（重试=重复提案）、无乐观锁（35 对象零 version 列，
  "后写胜出"风险靠悲观锁窗口缓解）、审批不绑提案内容指纹（批的可能不是看的那版）。
- **配置版本化**：SYSTEM_PROMPT 裸常量、llm_calls 无 prompt_version；规则逻辑改动无版本痕。
- outbox 是停靠表非真机制（仅 reschedule 一动作入队、永远 pending、无 worker）。

### ② 项目架构

**真有**：模块化单体（app/pipeline/agent/apps 四层职责清晰）；**本体 JSON 单一权威源 +
三座桥代码生成（权限/工具/模型/DDL 全从声明生成）——这是 Monday 没有的独门杠杆**（详见
§二）；决策日志 V1-V14 实质就是 ADR 实践；Domain 层零框架依赖（actions 是纯函数）。

**真缺**：全仓零 tenant_id（V14 接缝①）；API 契约层未硬化（无统一响应信封/409 冲突语义/
游标分页/Idempotency-Key 头）；SQLite 单文件形态（企业级=Postgres 路线，但单租户期不必迁，
可用桥3 生成双方言 DDL 留接缝）。

### ③ 页面布局

**真有**：驾驶舱七区指挥墙+四段下钻+角色缩放（同视图、数据按角色服务端过滤脱敏，本日 ops
亲验金额脱敏正确）；透视镜 15 视图（建造者工具，单一视角是有意设计）；治理控制室诚实空态。

**真缺**：视图 100% 硬编码组件（V14 接缝③ ViewConfig）；空/错/无权三态未系统化设计（有局部
好实践无全局约定）；汇总数字"下钻回来源+计算时点"未普遍化（有口径 docstring，无 UI 级溯源）。

### ④ 能力构造

**真有**：35 对象/56 关系/32 动作/21 规则/12 状态机；字段类型注册表实质已有（本体 properties
→Pydantic/DDL 生成）；关系图物化（object_relationships 6998 边）；行级建模（SO/PO 双行级）。

**真缺**：
- **自动化零用户可定义**：唯一工作流硬编码在 Python（派单→提案→审批→关闭）。Monday 的
  分法（单对象轻 Recipe / 跨对象带审批的版本化 Workflow DAG 两套引擎）我们两套都没有——
  用户(Daniel)加一条"若 X 则提案 Y"必须改代码。这也是裁决题2（规则 DSL）的真正归宿。
- Mirror/Rollup 派生字段声明缺位（驾驶舱聚合全是手写 SQL，源变不失效）。
- 发布前静态检查只覆盖本体（ontology_lint），未来 Recipe 需同等 lint。

### ⑤ AI 能力

**真有**：真 MCP 工具面（18 工具、角色过滤、声明脱敏、审计落 llm_calls）；出境闸门（PII/
预算/熔断）真代码；proposal-only + 冻结区生成层排除（今日 A-1 后人类决策通道也物理隔离）；
影子测量台真代码（档2 145 行真数据，档1 真 AI 长跑今日进行中）；29 题 eval 入发版门。

**真缺**（路 C 价值核心区）：
- **放权门禁只有规格没有引擎**：阶梯数字停在文档占位，代码里没有任何逻辑去算"当前一致率
  是否跨阈值"并据此改变工具授权——是给人看的判据草案，不是自动放权机制。
- **无持久 Agent runtime**：现状是无状态单发问答循环，没有可暂停等审批/可断点恢复/步数与
  预算硬上限/防打转的状态机。AI 干不了"跨会话的多步活"。
- 工具授权无 R0-R3 风险分级（更无参数敏感级别：改 1 条 vs 改 100 条同权）。
- 置信度校准、"模糊/该拒答"与"运维故障"金标分层、基线差量回归、p95 成本门：均缺。
- G-Shadow 本日勘误：--llm 档 MCP 子进程未透传临时副本路径，连真库（业务写=0 有 G-Trace
  铁证，但 llm_calls 审计落真库，"业务库全程只读"措辞不成立）；escalation recall 切片、
  样本量 CI 列规格已写代码未写。

## 二、关键判断：我们的独门杠杆改变了搬运经济学

Monday 蓝图里最重的地基（Command 信封、权限策略、类型注册、契约先行）在它那里是**手写的
工程税**；而本项目已有**本体→代码三座桥**。这意味着：给 32 个动作统一加 Command 信封/幂等键/
version 列/tenant_id 列，主要工作量是**改声明+改生成器**，而不是逐文件手改——Monday 要 37 个
工作包干的事，我们有相当一部分能用"第四座桥"的方式生成出来。**结论：地基类提升对我们比对
Monday 便宜一个量级，不该按它的顺序抄它的工期，该按我们的杠杆重排。**

## 三、三条路线候选

### 路线甲「AI 纵深优先」
波1 AI（放权引擎+runtime+R0-R3）→ 波2 能力构造（Recipe）→ 波3 地基与接缝。
优点：最快见"智能"；缺点：runtime 的持久写需要幂等/版本护栏，先建后补=返工债。

### 路线乙「地基先行」（Monday 正统序：Foundation→Domain→…→AI）
波1 Command 总线+乐观锁+幂等+契约+tenant_id → 波2 AI → 波3 Recipe/ViewConfig。
优点：零返工；缺点：数周纯管道零可感提升，且单用户场景并发收益部分是理论值。

### 路线丙「三波纵向切片，每波都交付看得见的聪明」★推荐
- **波1「AI 可信度可测可放权」**：放权门禁引擎（从 shadow.sqlite 实时算各域一致率+样本量
  CI，治理控制室显示各域当前档位，跨阈值自动改工具授权生成——只读侧智能，不碰写路径故
  无返工债）+ G-Shadow 勘误修复（temp 透传/recall 切片/CI 列）+ prompt_version 版本机。
  吃今天长跑落下的真数据。可感：**系统自己知道"哪个域的 AI 建议可信到什么程度"并自动放/收权**。
- **波2「Command 写总线 + 持久 Agent runtime」**：统一写信封（command_id/幂等键/乐观锁
  version/审批绑提案指纹）经桥式代码生成铺满 32 动作，/actions、/decisions、Streamlit 全走它；
  tenant_id 列随桥3 DDL 再生成顺手预留（接缝①②一次成）；API 契约硬化（信封/409/游标）；
  其上建持久 Agent runtime 状态机（暂停等审批/断点恢复/预算上限/防打转——runtime 的每步
  就是一条 Command，天然幂等）。可感：**AI 能安全地干多步活，全程可暂停可追溯**。
- **波3「用户可定义：Recipe 自动化 + ViewConfig」**：触发-条件-动作 Recipe（版本化+lint+
  影子模式先跑再放行，复用波1 门禁思想）+ 驾驶舱/透视镜视图定义抽成 ViewConfig 数据
  （接缝③）。可感：**Daniel 不写代码就能加自动化规则、改画面布局**。
- 页面三态系统化、A-2 回放、数字溯源：作为持续小步嵌入各波，不单列大波。
- 风险如实：波1 与波2 有一处顺序代价——门禁引擎先于 Command 总线，若引擎需要写授权变更
  记录，先用现有 action_log 语义，波2 迁移（受控小返工，换取真数据当天可用）。
