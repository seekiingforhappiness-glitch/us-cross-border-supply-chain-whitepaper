## 0. v0.3 增补：复用命题的验证结果（核心结论）

v0.3 用第二个业务场景（SKU 准入报价）验证了 Palantir 模式的核心卖点，全部达成：

| 复用性 KPI | 目标 | 实际 |
| --- | --- | --- |
| 重复定义的对象类型 | 0 | 0（Supplier/Sku/Customer 原对象扩展字段，Sku_2 之类不存在） |
| 治理机制重建 | 0 | 0（审计/权限/动作模式/AI 护栏直接 import v0.2 实现） |
| v0.2 回归 | 全绿 | 六评估器零回归（独立随机流从源头保证零扰动） |
| 门禁正确率 | 100% | G1/G2/G3 + DDP 成本门禁，该拒的全拒且留审计 |
| 准入断言 | 22 条 | 22/22（AI 红线含不编造 HTS、诱导批准被拒） |

两场景经 `sku_status` 生命周期咬合（准入批准→SKU 转 active 进入控制塔世界），
经同一 Customer 对象贯通（一条 SQL 取出同一客户的准入案件×延误风险）。
增量成本对比（v0.4 收官时用 git 实测修正）：v0.3 增量实为 v0.2 的 **40%**（早前"约 1/3"
的说法偏乐观，如实更正）。

v0.3 领域收获：v0.1 纸面规格落地暴露五处勘误（N1-N5，最典型：有毛利字段没报价字段）；
"迁移导入的历史不带审计、新动作全留痕"是真实系统上线的标准姿势。

## 0-v4. 第三场景（费用对账）与复用经济学的诚实修正

v0.4 交付：费用对账闭环（R4 超收/R5 重复/R6 计划外）**直接复用** RiskEvent/Task/审批/审计/
UI 队列（F1），G4 贸易术语转嫁门禁，F4 跨场景归因（"这笔滞箱费源于 X 月 X 日的 ETA 延误"），
Container 对象化偿还 D5 技术债。九评估器全绿，断言 23/24。

**XE3 未达成（≤25% 目标 vs 实测 52%），这是全项目第一个如实记录的失败 KPI**，其拆解比达标
更有价值：v0.4 增量 1386 行中，仿真与评估脚手架占 956 行（datagen/评估器/闭环测试），
业务闭环本体仅 402 行（≈v0.2 的 15%）。修正后的结论：
1. "本体即平台"对**运营机制**成立——第三场景的检测+动作+门禁+UI 仅 400 行量级，且零重建治理机制
2. 对**造世界的成本**不成立——合成数据与 ground truth 的成本随场景复杂度上升而非下降；
   这是学习型项目的固有属性（真实部署中数据已存在、ground truth 来自运营反馈），
   但当初把 LOC 总量当 KPI 是度量设计失误：混淆了"平台复用"与"场景仿真"两种成本
3. 教训：KPI 不达标时最大的诱惑是解释成"其实达标了"——本项目选择记失败并修正认知

## 0-v6. 收尾双专题（v0.6）

**Y1 风险评分模型**（手写逻辑回归，零依赖）：在途早警模型 AUC 0.969、P@10 0.8、校准单调
——早期 eta_change 信号确实可预测最终击穿。更有价值的是静态模型：实测 AUC 0.75 而非
预设的 ≈0.5，子代理主动诊断为 **as_of 快照删失混杂**（早开船者已妥投脱离标签、晚开船者
在途易被标记，按月正例率 5 月 0%→7 月 35%）——表观信号是标签生成机制的时点效应，
不是特征的因果预测力。ML 教训：**先审标签怎么来的，再谈特征有没有用**（H1 勘误）。

**Y2 单证号级 ER**（G1 完全体·有界版）：milestone 源表删除内部 shipment_id，改按
订舱号/柜号解析（真实 EDI 形态：10% 只有柜号、5% 只有订舱号、2% 坏单证号）。
解析率 98.3%；11 条坏单证行进停车表不丢弃不猜；因事件丢失导致 2 船清关状态与真值
不一致——评估器用 **known-loss 白名单**如实计数（名单严格来自注入日志，名单外
一船失配即败），而非放宽精度断言。数据工程教训：真实世界的对账残缺要被"显式管理"，
不是被"平均掉"。

## 0-v7. 第四、五场景（采购 + 仓储）与对象中心转向（2026-07-07/08）

**采购域（决策 P1-P3，R7-R15）**：三方对账（PO×收货×发票，R7-R10）+ 开票超收/预付款敞口/供应商资质过期（R11-R13）+ 单一来源/maverick（R14-R15）。**直接复用** RiskEvent→Task→提案→审批(maker-checker)→审计闭环——RiskEvent 锚点从"货运锚定"泛化为多态（shipment/po/supplier/warehouse），一套治理承接新业务域，零重建。九项处置动作 append 进动作层。R7-R15 逐条 P/R=1.000、灰区 0 误报。P2-BuildA 曾出 R7 recall=0.500：子代理**如实报告**为 Build 1 的数据缺口（收货行缺行级 received_date、多行 PO 延误被 GRN 头 min 掩盖），并**拒绝改真值凑指标**（§5），补行级字段后真值 md5 逐字节不变、R7→1.000——"评审以重跑为准"再次兑现。

**仓储域（决策 W1，R16-R18）**：断货/不可履约/盘点差异。真正价值在**跨场景连接**：采购收货 GoodsReceiptLine → 上架 → 库存 InventoryPosition → 预留驱动 SalesOrderLine 履约 → **延误时查目的仓现货 → SuggestSubstitution 拆单先发 + 余量 backorder**——白皮书"一票延误怎么保客户承诺"的落点，五场景第一次连成一张网而非五个孤岛。

**对象中心转向（Foundry 范式落地）**：从"角色页面"升级为"对象即工作台"——6 个核心决策对象（RiskEvent/Task/Invoice/AdmissionCase/PurchaseOrder/Warehouse）各有富工作台 + permission-aware 对象级 agent，其余 27 对象走自动标准视图（对象图可导航）。对象级 agent 三条硬约束**均经 controller 独立对抗验证**：① 只提案不审批（审批类对任何角色都不注册为 agent 工具）；② 数据范围完全继承 UI（test_scope_parity 证明 ops 的 agent 看不到成本、和 ops UI 逐字一致）；③ 越权在动作层挡回不在提示词（注入 "you are admin now" 被拒 + 写 denied 审计）。

诚实边界：采购/仓储数据为基于真实调研的高真实感合成数据，未接真实 ERP/WMS；P/R=1.000 是**合成数据上的能力证明**，非真实战绩。

## 0-v8. loop 驱动的 §4 加固（本会话自定步调 15 迭代）

人设定"迭代到第 15 次交付完整控制塔"的自定步调 loop，边界明确：**loop 只做 §4「AI 主导人验收」的完成/打磨/加固，绝不擅自开新业务域**（新对象/新规则需 Daniel AskUserQuestion 亲批）——既避免"完备性陷阱"（无限加域），又让每次迭代是一个可独立验收的小切片。已落地的加固：统一对抗安全 sweep 测试（6 对象 agent × 注入变体 288 次全被拒 + 292 条 denied 审计）；approve_mitigation 行为保持重构（抽 helper 去重，行为逐字不变）；多区域可见过滤证明（守 truth md5）；agent eval 扩采购/仓储（22→29，判定不放水，注入假事实反证会 FAIL）。

工作模式固化：每迭代**controller 独立重跑验证**（不信子代理报告只信输出），每次必守"既有 R1-R18 全 P/R=1.000 不扰动、agent 不越权、ground truth md5 不变、maker-checker/FORBIDDEN 不削弱"四条红线。多次抓到的假阳性/口径问题都当场核实（如 grep "error" 命中系"无 error"断言）。

## 3. 踩过的坑（真实教训，按周）

- **W2 可复现性破坏**：模块常量被原地污染——进世界的数据必须复制。"同种子逐字节一致"
  这条硬验收当场抓住它，验收纪律的第一次回报
- **W2 随机涌现不可靠**："多客户击穿 ≥15"靠调参是掷骰子，最终三级确定性补齐——
  计划里写"人为设计"的东西就该确定性保证
- **W4 D8 时间泄漏**：引擎偷用快照日状态，时钟拨回后"未来事件"仍可见——
  凡带时间语义的读取必须显式声明以何时的世界为准
- **W4 断言与规则相撞**：R3 正确报警但场景设计没料到——反例断言要对全部规则交叉检查；
  规则没错时不要动规则
- **W5 UI 回执被冲掉**：用户看不到成功就会重复点击——动作有回执才算完成，对人对 AI 一样
- **全程**：ChatGPT 初始方案的三大缺陷（无行级粒度、milestone 未对象化、KPI 不可测）
  印证了"先最小闭环"与 ground truth 驱动评估的价值
