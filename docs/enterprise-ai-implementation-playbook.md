# 数智供应链控制塔 AI 实施手册

版本：v1.0  
日期：2026-07-12  
适用范围：从当前 v0.9.0 仿真原型推进到首个设计伙伴的可控试点  
研究母本：Stanford Digital Economy Lab, *The Enterprise AI Playbook: Lessons from 51 Successful Deployments*（2026-04）

> 本手册不是新路线图，也不批准新增范围。它把斯坦福报告的实证规律翻译为本项目的实施纪律、阶段门、指标与现场动作。若与 `docs/superpowers/specs/2026-07-12-merge-resolution-v2.2.md`、当前执行期 plan 或决策日志冲突，以上游文件为准。

## 0. 先给结论

本项目不缺“一个更聪明的模型”，缺的是把现有对象-关系-动作网络接进真实工作流后，持续完成五件事：

1. 找到一个业务人员正在“淹死”的高频痛点，而不是展示 AI 能做什么。
2. 把实际流程、异常、输入介质和裁决理由变成可回放的数据。
3. 让 AI 先做提取、归类、简报和提案，人保留事实确认、审批、对外承诺与花钱动作。
4. 在上线前定义业务价值、质量、采用、风险四类指标，用真实基线做前后对照。
5. 每周由业务负责人清障；只有特定任务达到证据门槛，才从影子模式逐步放权。

当前正确顺序维持 **B（协调收件箱，已完成）→ C1（处置记忆）→ A（真实信息流入）→ C2/C3 → D**。斯坦福报告强化了这个顺序：先利用已有基础、沉淀工作知识和反馈闭环，再扩大接入与自动化半径。

首个实施目标不是“企业级规模化”，而是：**在一个设计伙伴、一个高痛点流程、一个可逆闭环内，证明系统能减少遗漏和查找时间、提高处置质量，并且不越权、不污染事实、不制造新的隐形劳动。**

## 1. 研究依据与证据边界

### 1.1 报告研究了什么

斯坦福数字经济实验室研究了 41 个组织、7 个国家的 51 个已产生可衡量价值的 AI 部署，覆盖多行业和多类职能。报告访谈生产环境中的高管与项目负责人，并在可能时用内部指标、项目计划和财务材料交叉验证。

报告的关键实证发现包括：

- 77% 的最难挑战属于变革管理、数据质量、流程重设计等“隐形成本”，不是模型技术。
- 61% 的成功项目此前至少经历过一次显著失败。
- 相似用例从数周到数年不等，主要差异来自高管赞助、既有基础和终端用户意愿。
- 所有可识别开发方法的成功案例都采用迭代方式；73% 刻意从小范围开始，63% 明确把试点定义为实验。
- 异常升级制案例的生产率提升中位数为 71%，逐项审批制为 30%；但报告明确提醒，这部分差异也来自任务类型不同，不能当作“越自动越好”的因果证明。
- 只有 6% 的案例一开始数据已完全就绪；在成功样本中，模型在 88% 的相关案例里也被用来解锁非结构化数据。
- 42% 的实施把模型视为可替换组件；常规任务中这一比例为 71%，复杂任务才更依赖模型能力。

### 1.2 不能从报告推出什么

这是成功案例导向、主要依赖受访者自报的样本，作者明确提示存在成功选择偏差，样本也不代表全部企业。因此：

- 不能把 71% 当成本项目收益预测或验收目标。
- 不能把“脏数据可用”误读为“不需要事实确认、数据治理和访问控制”。报告只说明 AI 可参与清洗和提取，不说明输出天然正确。
- 不能因 agentic 案例收益较高就直接取消人审；对外承诺、财务、合规等零容错/高损失任务恰是报告建议保留人审的领域。
- 不能把成功案例中的裁员比例当作本项目价值主张。对一个小型设计伙伴，避免漏单、缩短响应、保住客户和降低新人上手成本更可测，也更符合产品定位。

**证据判断：**报告对“组织和流程决定实施成败”的支持为高；对“异常升级制优于审批制”的因果强度为中；对本项目具体 ROI 数值没有直接证据。

## 2. 本项目的实施命题

### 2.1 业务命题

当跨境履约异常从聊天、邮件、Excel 或人工录入进入系统后，系统能把它锚定到对象图，算清影响，形成风险与协调任务，调用历史处置先例提出建议；业务人员确认事实并执行动作，所有决定与结果可回放。

### 2.2 人机分工

| 工作 | 默认责任 | 原因 |
| --- | --- | --- |
| 收集信息、提取候选字段、去重、归类 | AI 主做，人确认例外 | 高频、可逆、适合异常升级制，但候选不等于事实 |
| 对象关联、规则检测、影响金额计算 | 确定性代码 | 可测试、可解释，不应交给概率模型 |
| 根因简报、处置选项、外部话术草稿 | AI 提案 | 需要语义综合，但存在编造与语境误判风险 |
| 事实确认、审批、关闭、花钱、合规裁决 | 人 | 责任、权限和高损失边界不能转给模型 |
| 对客户/供应商/货代发送自由文本 | AI 起草，人签发 | 对外内容代表企业承诺，错误不可低成本恢复 |
| 处置记忆入库与技能版本生效 | 人批准，系统留血缘 | 防止 AI 用自己的输出证明自己正确 |

### 2.3 不实施什么

- 不以聊天机器人作为产品中心。
- 不用 LLM 替代已有 R1-R18 规则、状态机、权限和审计。
- 不在首个试点自建承运人直连、企微外挂或全套企业集成平台。
- 不在接真实数据前默认把个人信息或商业敏感数据发往境外模型。
- 不以“替代多少人”作为首个试点唯一商业论证。
- 不因单次准确就开放自动审批、自动对外发送或自动花钱。

## 3. 实施前置：先确认值得做

在写 C1/A 代码前，由 Daniel 完成 8-10 家陌生货主和 3 家货代的 Mom Test 访谈轨。每次只追问已发生的行为：

1. 最近一次延误/费用异常是怎么发现的？从哪条消息到哪张表，中间经过谁？
2. 最近一次因漏看、晚处理或交接丢失造成了什么损失或返工？能否拿出原始记录？
3. 现在为避免这件事，每周实际花多少时间，谁最痛，谁有权改流程和付费？

候选用例按下列六项 0-2 分打分：发生频率、单次损失、用户痛感、数据可获得性、结果可测性、错误可恢复性。首个切片必须满足：

- 总分至少 9/12；
- 有明确日常使用者和业务 sponsor；
- 4-8 周内可观察结果；
- 错误能被人发现并回滚；
- 不需要新增业务域才可闭环。

若访谈显示用户最痛的是“消息遗漏和催办”，以协调收件箱为入口；若最痛的是“老师傅离职后没人会处理”，以 C1 处置记忆和新人上手包为入口。不要因当前代码擅长什么而反向挑问题。

## 4. 六阶段实施法

### 阶段 0：建立基线与责任（1 周）

**目标：**在 AI 介入前看清真实流程和成本。

业务 sponsor 与技术 owner 共同完成：

- 选定一个流程、一个团队、一个业务负责人；画出从信号出现到风险关闭的当前流程。
- 采样至少 20 个近期真实事件，记录输入介质、参与人、等待点、返工点、最终结果。
- 记录连续两周基线：首响时间、结案时间、遗漏/超期、查找时间、重复录入、升级次数。
- 建立每周 30 分钟 sponsor 清障会，不做进度汇报会；议程只回答阻塞、决策、资源和风险。
- 明确数据授权、保留期、删除/导出方式、模型通道和禁止上传内容。

**阶段门 G0：**没有真实使用者、业务 sponsor、可测基线或合法数据路径，停止开发。

为什么这样建：斯坦福案例中相似技术的周期差异主要来自组织条件；业务+技术共同赞助优于技术团队单推。项目当前最大未知也不是模型能力，而是设计伙伴是否真的愿意改变工作方式。

### 阶段 1：C1 处置记忆最小闭环（2 周）

**目标：**让每次处置成为下次提案可引用的证据，而不是只留一条动作日志。

每条处置记忆至少包含：

- 情境快照：对象 ID、风险类型、严重度、影响金额/订单、时点与数据版本；
- AI 提案：模型/provider、prompt/skill 版本、提案正文、引用的先例；
- 人的决定：采纳/修改/拒绝、选择理由、审批人和时间；
- 实际结果：是否解决、耗时、成本、客户/供应商反馈、是否复发；
- 质量标签：事实错误、建议无效、权限问题、未覆盖的新情形。

检索只返回相同业务域与可解释相似条件的少量旧案；提案必须显示“为什么相似”和对象引用。未经人工确认的候选事实、AI 自评和模拟结果不得进入正式先例库。

**阶段门 G1：**用固定样本证明任何提案都能回放“当时看到了什么、引用了什么、人为何改、结果如何”；删除或屏蔽某条先例后，系统不得暗中继续引用。

为什么这样建：报告把知识未被捕获列为第二大失败根因。项目已有 action_log，但“做了什么”不等于“为什么这样做”；决策血缘才是 C1 真正的训练材料和护城河。

### 阶段 2：A 信息流入的影子模式（2-4 周）

**目标：**先证明 AI 能把真实输入变成可靠候选，不直接改变业务事实。

按真实介质普查选择一个入口：手工粘贴、CSV 或邮件正文三选一。流程为：

```text
外来内容 → 恶意指令/敏感信息检查 → AI 提取候选 → 去重/对象匹配
→ 待确认队列 → 人确认 → 写入对象层 → 规则检测 → 风险/任务
```

必须具备：输入原文留存或可验证引用、幂等键、失败重试、毒信队列、字段置信与空值、人工录入兜底、删除与重放。任何提示注入文本只能作为数据，不能变成系统指令。

**阶段门 G2：**至少 30 个真实样本；关键字段查全率和查准率分别报告；0 个跨租户/越权暴露；0 个未经确认候选直接进入事实层；所有失败可见且可重放。

为什么这样建：报告发现只有 6% 的案例数据完全就绪，AI 可帮助解锁非结构化数据；但成功做法是建立访问层和反馈闭环，不是跳过数据边界。影子模式让失败便宜且可观察。

### 阶段 3：受控试点（4-8 周）

**目标：**在真实工作中验证价值，不追求全自动。

上线范围限定为一个团队、一个用例、一个班次或客户子集。系统每天输出异常队列与提案；业务人员仍确认所有事实和动作。技术 owner 每周检查错误簇、延迟、成本和人工负担；业务 owner 每周检查是否真的少漏、少找、少返工。

试点采用 A/B 不现实的情况下，用“上线前两周基线 vs 上线后同长度窗口”，同时记录订单量、人员变化和异常量，避免把淡旺季误当 AI 收益。不得把模拟环境的 R/P=1.000 当真实效果。

**阶段门 G3：**质量红线全过；周活跃使用者达到目标；至少连续 4 周数据；业务价值指标改善且人工负担没有转移到新的隐形步骤；用户愿意继续使用。

为什么这样建：斯坦福报告强调 KPI 必须在部署前定义，成功项目全部迭代。当前项目的仿真评估证明代码一致性，不证明真实流程价值；两类证据必须分开。

### 阶段 4：分域渐进放权（持续）

**目标：**只对成熟、可逆、低损失任务减少人审。

每个“任务×场景×动作”独立晋级，不按整个 agent 一次性放权：

| 等级 | 系统行为 | 适用示例 |
| --- | --- | --- |
| L0 观察 | 只记录人的做法 | 新规则、新输入源 |
| L1 影子 | AI 给结果但不展示或不生效，与人决定对比 | 对象匹配、风险分级 |
| L2 提案 | AI 展示提案，人确认后生效 | 处置建议、对外话术 |
| L3 异常升级 | 低风险常规项自动处理，人审异常/抽样 | 去重、格式标准化、内部提醒 |
| L4 受限自治 | 在额度、对象、时间窗内执行，可一键撤销 | 仅未来经批准的低风险内部动作 |

晋级最低证据：至少 30 个经人工确认样本、连续 4 周、一致率达到预先批准阈值、严重错误为 0、回滚演练通过、成本在预算内。任何严重错误、权限事故或漂移立即降级；样本不足就保持原级，不降低门槛。

冻结区永久不自动晋级：审批、关闭、花钱、合规裁决、自由文本对外发送、权限和审计配置。

为什么这样建：报告中的异常升级制高收益发生在高频、可恢复任务；逐项审批适合受监管和高风险工作。按动作分域比按“整个 AI 同事”放权更符合证据，也延续项目 maker-checker 铁律。

### 阶段 5：复制或停止（第 6-8 周商业裁决）

只有同时满足以下条件，才复制到第二用例或第二客户：

- 原用例连续 4 周稳定，业务 sponsor 愿意为继续使用承担预算或明确资源；
- 至少一个业务价值指标改善，且能解释因果链和混杂因素；
- 安全、权限、审计、导出、失败恢复和模型降级已实测；
- 新场景与现有对象/动作有显著复用，不需要偷偷扩域；
- 团队能够在无开发者手工救火的情况下运行日常流程。

否则执行三岔路：继续同一用例补证据、缩小/调整问题，或停止。出现第二家非亲友付费客户后，再按既有裁决考虑独立产品 repo 和通用化。

## 5. 指标体系：四张成绩单

指标必须在试点前写出定义、数据源、基线、目标、观察窗和负责人。不能只看准确率，也不能只看省人。

### 5.1 业务价值

| 指标 | 定义 |
| --- | --- |
| 首次响应时间 | 外部信号出现至负责人首次确认/动作的中位数与 P90 |
| 风险结案时间 | RiskEvent 创建至关闭的中位数与 P90 |
| 超期/遗漏率 | 应处理事件中未在 SLA 内确认或关闭的比例 |
| 处置避免损失 | 仅记录有对照依据的加急、滞箱、断货或客户赔付差额；无法证实时标“未证实” |
| 新人上手时间 | 新专员独立完成指定情景并通过断言所需时间 |

### 5.2 AI 与流程质量

| 指标 | 定义 |
| --- | --- |
| 关键字段 Precision / Recall | 对人工确认真值逐字段计算，不用 AI 自评 |
| 提案采纳率 | 原样采纳、修改后采纳、拒绝分开报告 |
| 严重错误率 | 越权、错客户、错金额、错承诺、无来源事实单独计数 |
| 先例命中有效率 | 引用旧案中经人判断真正相关的比例 |
| 重放一致性 | 同一输入、版本和 `as_of_date` 能否重建当时结果 |

### 5.3 采用与组织

| 指标 | 定义 |
| --- | --- |
| 周活跃使用率 | 目标用户中每周完成至少一个真实闭环者占比 |
| 旁路率 | 实际事件中绕开系统、仍只在群聊/Excel 处理的比例 |
| 人工触点数 | 每事件所需复制、确认、补录、催办次数，防止隐形劳动转移 |
| 用户纠正闭环率 | 人工纠正中已分类、进入评估或产品改进的比例 |

### 5.4 风险与运行

| 指标 | 定义 |
| --- | --- |
| 权限/数据事件 | 跨租户、越权读取、敏感信息外发，目标恒为 0 |
| 不可见失败率 | 失败但没有进入告警、毒信队列或人工兜底的比例，目标恒为 0 |
| 单事件推理成本 | 按任务和模型拆分，含重试与影子运行 |
| 可用性与降级 | LLM 不可用时规则引擎、队列和人工录入是否仍可工作 |
| 回滚时间 | 从发现坏版本到恢复稳定版本的时间 |

## 6. 运行与治理机制

### 6.1 Sponsor 的每周动作

Sponsor 不是签预算的人。每周清障会必须产出：

1. 本周最大的业务阻塞及责任人；
2. 一个需要业务裁决的语义问题；
3. 一个应修复的流程而非模型问题；
4. 红线事件和降级决定；
5. 下周只验证一个最小假设。

业务 sponsor 定义成功、推动采用并裁决业务语义；技术 owner 保证实现、评估与运行；一线 champion 提供样本、纠错和现场反馈。三者不能由“模型自己”代替。

### 6.2 变更闸门

以下变化必须跑全量相关评估和红线题：模型/provider、prompt、skill、检索策略、对象映射、动作参数、权限、输入解析器。结果按版本保存，生成者不得担任唯一验证者。

变更分级：

- 低风险：措辞、内部只读简报；聚焦评估通过后发布。
- 中风险：提取、匹配、风险分级、处置提案；影子回放+人工抽验后发布。
- 高风险：权限、写动作、对外内容、合规/金额；须人批准、回滚演练及完整审计，不允许静默发布。

### 6.3 失败预算

允许便宜、可恢复、能学习的失败，不允许隐蔽、跨权限、污染真值或对外造成承诺的失败。每次试验预先写：最大样本数、最大费用、可触碰对象、禁止动作、停止条件和回滚办法。

失败记录至少包括假设、证据、根因、损失、保留/回滚决定，以及新增的评估样本。不能因结果不达标而修改 KPI 或真值。

### 6.4 安全与模型策略

- 模型层保持可替换；按准确性、成本、延迟、隐私和地区合规路由，不以单一厂商能力作为产品护城河。
- 真实数据进入前完成 PI/敏感字段摘除、模型出境白名单闸门和已批准 provider 的真实评估。
- 交互式 AI 继承当前用户权限子集；无人值守流程使用独立服务身份、最小权限和独立审计。
- 原始外部内容永远按不可信数据处理；提示注入扫描失败时进入人工队列。
- LLM 失败时，规则引擎、对象查询、任务队列和人工闭环继续可用。
- 所有客户数据支持可导出和按授权删除；“越用越强”来自流程中的决策血缘，不来自锁住客户数据。

## 7. 现场执行清单

### 上线前

- [ ] 一个真实痛点、一个 owner、一个 sponsor、一个用户组
- [ ] 当前流程与两周基线已记录
- [ ] 数据授权、模型通道、保留/删除/导出规则明确
- [ ] 输入失败、重复、注入、越权、LLM 不可用均有测试
- [ ] KPI 定义、目标、观察窗与停止条件已签字确认
- [ ] 用户按实际角色走通“发现→确认→提案→审批→处置→关闭→审计”
- [ ] 回滚与人工兜底演练通过

### 每日

- [ ] 检查毒信队列、未确认候选和超时协调线程
- [ ] 检查严重错误、无来源陈述和权限拒绝
- [ ] 抽样 AI 提案与人工最终决定的差异
- [ ] 记录系统外旁路事件，不把“没进系统”误算为“没发生”

### 每周

- [ ] Sponsor 清障会完成并留决定
- [ ] 四张成绩单更新，模拟与真实证据分开
- [ ] 人工纠正归因到数据、流程、规则、检索、prompt 或模型
- [ ] 新评估样本由人确认后入库
- [ ] 审查有无晋级/降级任务；样本不足则不动
- [ ] 向设计伙伴披露管理员修改、失败、成本和已知盲区

### 试点结束

- [ ] 对照基线报告业务结果与混杂因素
- [ ] 报告总人工投入，不能只报 token/API 成本
- [ ] 报告严重错误、被拒提案、旁路率和不可见失败
- [ ] 用户亲手走查并对断言打勾
- [ ] 明确裁决：复制、继续补证据、缩小/转向或停止

## 8. 对当前项目的直接差距

| 已有基础 | 实施前仍缺 |
| --- | --- |
| 34 个对象、18 条规则、动作闭环、7 角色权限、审计 | 真实设计伙伴的流程基线与可用数据授权 |
| 协调收件箱与跨主体处置动作 | C1 决策血缘、结果记录和可解释先例检索 |
| Claude CLI grounding、对象级简报、越权拒绝 | 真实数据进入前的 PI 摘除、出境闸门与生产 provider 策略 |
| 固定种子、规则评估器、agent 评估题 | 真实样本评估集、变更分级闸门和线上漂移/失败指标 |
| maker-checker 与 proposal-only | 每个任务的自主权等级、晋级证据和一键降级机制 |
| 仿真数据完整闭环 | 运维骨架：幂等、重试、毒信、可观测、备份恢复、成本预算 |

近期一个验收点只做 **C1 处置记忆→更好提案**。它的成功标准不是“多建一张表”，而是：同类风险再次出现时，用户能看到相关旧案、当时理由和实际结果；用户的采纳/修改/拒绝又能成为下一轮经确认的证据。A 信息流入在 C1 之后，且首次接真实数据前必须重新走 §3 人类裁决。
